## શરૂઆતમાં — મોટી તસવીર (Big Picture)

ઘરે રસોઈ કરતી વખતે આપણે વાસણ ધોઈએ, હાથ સાફ કરીએ, સામગ્રી તાજી છે કે નહીં જોઈએ — પણ કંઈ ખોટું થાય તો
મોટે ભાગે "ફરી બનાવી લઈશું" એટલું જ પરિણામ હોય. દવા બનાવતી ફેક્ટરીમાં એવું નથી — અહીં **દરેક પગલું
લખાયેલું (documented), ચકાસાયેલું (verified), અને જવાબદાર વ્યક્તિની સહી સાથે** હોવું જોઈએ, કારણ કે
ભૂલનું પરિણામ "ફરી બનાવી લઈશું" નહીં, પણ "કોઈ દર્દીને નુકસાન થયું" હોઈ શકે છે.

આ system બે મોટા ભાગમાં વહેંચાયેલ છે:

1. **ભાગ ૧ — Operations（ઉત્પાદન)**: દવા ખરેખર કેવી રીતે બને છે — equipment સાફ કરવાથી માંડીને, ભરવા,
   પેક કરવા, અને છેલ્લે "આ batch બજારમાં મોકલવા માટે તૈયાર છે" કહેવા સુધી.
2. **ભાગ ૨ — Quality System (ગુણવત્તા સંચાલન)**: જ્યારે કંઈક ખોટું થાય (અથવા થવાની શક્યતા હોય) ત્યારે
   શું કરવું — કેવી રીતે શોધવું, તપાસવું, સુધારવું, અને ભવિષ્યમાં ફરી ના થાય એની ખાતરી કરવી.

# ભાગ ૧ — Operations Modules (ઉત્પાદન પ્રક્રિયા)

MJ-PFS સિરીંજ બનાવવાના ક્રમમાં આ modules આવે છે:

```
Equipment સાફ કરવું (Cleaning)
   → Line Clearance (જગ્યા ચકાસવી — પાછલું batch કંઈ બાકી નથી)
   → Sterilization (equipment/ફિલ્ટર જીવાણુ-મુક્ત કરવા)
   → Environmental Monitoring (રૂમની હવા ચોખ્ખી છે એ ચકાસવું)
   → Aseptic Operation (ખરેખર દવા સિરીંજમાં ભરવી — સૌથી સંવેદનશીલ પગલું)
   → Packaging (લેબલ લગાવવા, બોક્સ કરવા)
   → QA Review (batch નો આખો રેકોર્ડ બીજી વાર ચકાસવો)
   → Release (બજારમાં મોકલવાનો છેલ્લો નિર્ણય)
   → Yield & Reconciliation (કેટલું વાપર્યું, કેટલું બન્યું — ગણતરી સરખી છે કે નહીં)
   → Genealogy (કોઈ પણ વસ્તુ ક્યાંથી આવી, ક્યાં ગઈ — history શોધવા માટે)
```

સાથે **Equipment/Devices** module છે, જે ઉપરના લગભગ દરેક પગલાને ટેકો આપે છે ("આ equipment વાપરવા
લાયક છે કે નહીં" કહીને).

## ૧.૧ Cleaning (સફાઈ)

**સાદી ભાષામાં:** એક equipment (દા.ત. ભરવાનું મશીન — "Filler") પર એક દવા બનાવ્યા પછી, બીજી દવા એ જ
મશીન પર બનાવવી હોય તો પહેલા મશીન **સંપૂર્ણપણે સાફ** કરવું પડે — જેમ ઘરમાં એક વાનગી બનાવ્યા પછી કડાઈ
ધોઈને જ બીજી વાનગી બનાવીએ છીએ, બસ અહીં એ "ધોવું" ખૂબ વધારે ચોક્કસ અને લખાયેલું (documented) હોવું
જોઈએ.

**શા માટે જરૂરી:** જો સફાઈ બરાબર ના થાય, તો પાછલી દવાનો અંશ (residue) નવી દવામાં ભળી શકે
(cross-contamination) — જે દર્દી માટે ખતરનાક બની શકે (દા.ત. allergy, ખોટી અસર).

**ઉદાહરણ:** Filler-01 મશીન પર MJ-PFS નું એક batch પૂરું થયા પછી, સફાઈ કરનાર વ્યક્તિ (Sanitation
Operator) સફાઈ શરૂ કરે → દરેક પગલું (disassemble, rinse, chemical apply, ફરી rinse) નોંધે → "પૂરું
થયું" સહી કરે → **બીજી, અલગ વ્યક્તિ** (QA Reviewer) આવીને ચકાસે કે ખરેખર ચોખ્ખું છે કે નહીં, અને પોતે
સહી કરે. આ બે-વ્યક્તિ ચેક (independent verification) ખૂબ મહત્વનું છે — જે વ્યક્તિએ સફાઈ કરી, એ જ
વ્યક્તિ "ચોખ્ખું છે" કહી ના શકે, કોઈ બીજાએ confirm કરવું જ પડે.

**જો આ ના હોય તો:** કોઈ પણ મશીન ગમે ત્યારે, ગમે તેટલું ગંદુ હોવા છતાં વપરાય શકે — અને કોઈને ખબર જ ના
પડે કે ખરેખર ચોખ્ખું હતું કે નહીં.

## ૧.૨ Line Clearance (જગ્યા ચકાસણી)

**સાદી ભાષામાં:** કોઈ પણ નવું batch શરૂ કરતા પહેલા, એ જગ્યા (room/area) માં **પાછલા batch નું કંઈ પણ
બાકી ના હોવું જોઈએ** — ના કોઈ material, ના કોઈ label, ના કોઈ કાગળ. જેમ રેસ્ટોરન્ટમાં એક ટેબલ ખાલી
કરીને ફરી use કરતા પહેલા વેઈટર આખું ટેબલ સાફ કરીને ચકાસે કે કંઈ પાછલા ઓર્ડરનું બાકી નથી.

**શા માટે જરૂરી:** જો પાછલા batch નું કોઈ material/label ભૂલથી રહી જાય, તો એ નવા batch સાથે ભળી જઈ
શકે — ખોટી દવા ખોટા label સાથે જઈ શકે, જે ખૂબ ગંભીર ભૂલ છે.

**ઉદાહરણ:** AREA-GRADE-C રૂમમાં નવું batch શરૂ કરતા પહેલા, એક checklist ચકાસાય છે — "Material કંઈ
બાકી નથી?", "Label કંઈ બાકી નથી?", "Equipment ખરેખર યોગ્ય/ચોખ્ખું જ છે?" — બધું Pass થાય તો જ આગળ
વધી શકાય.

**જો આ ના હોય તો:** Packaging (પેકિંગ) જેવા પછીના પગલાં પણ block થાય છે — સિસ્ટમ ખુદ "પહેલા Line
Clearance પૂરું કરો" કહીને રોકે છે.

## ૧.૩ Sterilization (જીવાણુ-મુક્ત કરવું)

**સાદી ભાષામાં:** ઈન્જેક્શન વાળી દવા માટે વપરાતું equipment/ફિલ્ટર **૧૦૦% જીવાણુ-મુક્ત (sterile)**
હોવું જોઈએ — જેમ હોસ્પિટલમાં ઓપરેશન પહેલાં સાધનો autoclave (ઊંચા temperature/pressure) માં
sterilize કરાય છે.

**શા માટે જરૂરી:** જો equipment sterile ના હોય, તો દવામાં જીવાણુ (bacteria) ભળી શકે — ઈન્જેક્શન
સીધું લોહીમાં જતું હોવાથી આ ખૂબ જોખમી છે (sepsis/infection થઈ શકે).

**ઉદાહરણ:** એક "master recipe" (Cycle Profile) નક્કી કરે છે કે કેટલા temperature/pressure પર કેટલો
સમય sterilize કરવું. પછી ખરેખર એક real sterilization run (Process Cycle) થાય — controller થી
temperature/pressure નો actual data રેકોર્ડ થાય. **ખૂબ મહત્વની વાત:** જે વ્યક્તિએ cycle ચલાવ્યું, એ
પોતે "Pass/Fail" નક્કી ના કરી શકે — ફક્ત **અલગ, independent reviewer** જ final નિર્ણય લે (accept કે
reject). વધારામાં, filter (પાણી/હવા ગાળવાનું સાધન) ને વાપરતા પહેલા અને વાપર્યા પછી બંને વાર ચકાસાય
છે કે એમાં કોઈ કાણું/leak નથી.

**જો આ ના હોય તો:** કોઈ પણ equipment "sterile છે" એવું ખોટું માનીને વાપરી શકાય — real proof વગર.

## ૧.૪ Environmental Monitoring — EM (રૂમની હવા/સપાટી ચકાસણી)

**સાદી ભાષામાં:** જે રૂમમાં દવા ભરાય છે, એ રૂમની **હવા અને સપાટી કેટલી ચોખ્ખી છે** એનું સતત ચકાસણી —
જેમ કોઈ ઓપરેશન થિયેટરની હવા સામાન્ય રૂમ કરતાં વધારે ચોખ્ખી રાખવી પડે.

**શા માટે જરૂરી:** હવામાં રહેલા particle/જીવાણુ સીધા ખુલ્લી સિરીંજમાં પડી શકે — equipment ભલે
sterile હોય, પણ રૂમની હવા ગંદી હોય તો એ કોઈ કામનું નથી.

**ઉદાહરણ:** દરેક ચોક્કસ જગ્યા (દા.ત. "Filler-01 ની બાજુની હવા") પર નિયમિત sample લેવાય છે — હવામાં
કેટલા particle/જીવાણુ છે એ ગણાય છે. જો limit ની બહાર જાય ("excursion"), તો સિસ્ટમ **આપોઆપ** એક
અલગ investigation record ખોલે છે — કોઈ manually યાદ રાખીને ખોલવું નથી પડતું.

**જો આ ના હોય તો:** રૂમની હવા ગંદી થઈ ગઈ હોય તોય કોઈને ખબર જ ના પડે, ત્યાં સુધી કે Aseptic Operation
(આગળનું પગલું) શરૂ જ ના થઈ શકે — EM જ પહેલું ચેક કરે છે.

## ૧.૫ Aseptic Operation (ખરેખર દવા ભરવી — સૌથી સંવેદનશીલ પગલું)

**સાદી ભાષામાં:** આ એ પગલું છે જ્યાં દવા ખરેખર ખાલી સિરીંજમાં ભરાય છે — સંપૂર્ણપણે જીવાણુ-મુક્ત
વાતાવરણમાં, જેમ કોઈ નવજાત બાળકના ઓપરેશન વખતે ડૉક્ટર જેટલી કાળજી રાખે, એટલી જ કાળજી અહીં રાખવી પડે.

**શા માટે જરૂરી:** આ પગલે સૌથી વધારે risk છે — દવા ખુલ્લી રહે છે, હવાના સંપર્કમાં આવે છે. કોઈ પણ
નાની ભૂલ (રૂમની હવા ખરાબ, equipment ખરાબ, કોઈ વ્યક્તિએ ખોટી રીતે અડક્યું) સીધી દવાને બગાડી શકે.

**ઉદાહરણ — આ module ની ખાસિયત:** શરૂ કરતા પહેલા, સિસ્ટમ **૪ અલગ-અલગ module ને એક સાથે** પૂછે છે:
"રૂમની હવા ચોખ્ખી છે?" (EM), "જગ્યા ચકાસાયેલી છે?" (Line Clearance), "Equipment વાપરવા લાયક છે?"
(Equipment), "ફિલ્ટર sterile છે?" (Sterilization). **આમાંથી એક પણ "ના" કહે તો Aseptic Operation શરૂ
જ ના થાય.** શરૂ કરવાની પરવાનગી ફક્ત Supervisor આપી શકે (સહી સાથે), પણ ખરેખર પૂરું કરવાની જવાબદારી
Operator ની (જુદી વ્યક્તિ) — બેલેન્સ/checks-and-balances માટે.

**જો આ ના હોય તો:** operator પોતાની મેળે, કોઈ ચેક વગર, ગમે ત્યારે દવા ભરવાનું શરૂ કરી શકે — ભલે રૂમ
ખરેખર તૈયાર ના હોય.

---

## ૧.૬ Packaging (પેકિંગ)

**સાદી ભાષામાં:** તૈયાર સિરીંજ પર label લગાવવું, બોક્સમાં પેક કરવું — જેમ કોઈ ઓનલાઇન ઓર્ડર પેક કરતી
વખતે બરાબર એ જ વસ્તુ, એ જ quantity પેક થાય એ ચકાસાય છે.

**શા માટે જરૂરી:** Label એ દવા ઓળખવાનો એકમાત્ર રસ્તો છે — જો label ની ગણતરી ખોટી જાય (વધારે/ઓછા
label વપરાય), તો કોઈ ખોટું label ખોટી જગ્યાએ જઈ શકે, અથવા કોઈ extra, બિનહિસાબી label બહાર જઈ શકે
(નકલી દવા બનાવવા માટે misuse થઈ શકે — એટલે આ ચેક ને "anti-diversion" પણ કહેવાય).

**ઉદાહરણ:** 1000 label issue થયા, તો છેલ્લે ગણતરી કરવી પડે — કેટલા લાગ્યા (applied), કેટલા પાછા
આવ્યા (returned), કેટલા તોડ્યા/નાશ કર્યા (destroyed), કેટલા reject થયા. **Issued = Applied +
Returned + Destroyed + Rejected** — આ ગણતરી બરાબર મળવી જ જોઈએ (balanced), નહીં તો run પૂરું જ ના
થાય. દરેક સિરીંજ પર લાગેલ unique serial number પણ track થાય છે — એક જ serial number બે વાર ક્યાંય
ના વપરાય એ ખાસ ચકાસાય છે.

**જો આ ના હોય તો:** કોઈ પણ વધારાનું label ક્યાંય જઈ શકે, કોઈને ખબર જ ના પડે.

---

## ૧.૭ QA Review (ગુણવત્તા સમીક્ષા)

**સાદી ભાષામાં:** Batch પૂરું થયા પછી, release કરતા પહેલા, એક "અંતિમ ચકાસણી" — આખા batch દરમિયાન
કંઈ પણ અસામાન્ય (exception/hold/correction) થયું હોય તો એ બધું ફરીથી, ધ્યાનથી જોવું. જેમ કોઈ પરીક્ષા
ની answer-sheet ચકાસ્યા પછી, result આપતા પહેલા બીજી વાર ભૂલો માટે check કરવી.

**શા માટે જરૂરી:** Batch દરમિયાન ઘણા નાના-મોટા events થયા હોય શકે — આ બધા events ને "ignore" કરીને
સીધું release ના કરી શકાય. કોઈ એક વ્યક્તિએ **આખું ચિત્ર** જોવું જોઈએ.

**ઉદાહરણ:** સિસ્ટમ **આપોઆપ** નક્કી કરે છે કે batch "સંપૂર્ણ ચોખ્ખું" છે, "અપવાદ (exception) સાથે"
છે, કે "block થયેલું" છે — આ ૩ status માંથી ફક્ત "સંપૂર્ણ ચોખ્ખું" હોય તો જ QA Reviewer "Review પૂરું
થયું" સહી કરી શકે. દા.ત. QC test (ગુણવત્તા ટેસ્ટ) હજુ પૂરો ના થયો હોય તો review "block" રહે.

**જો આ ના હોય તો:** Batch સીધું, કોઈ બીજી નજરે જોયા વગર, release થઈ શકે — જે ખૂબ risky છે.

---

## ૧.૮ Release (છેલ્લો નિર્ણય — બજારમાં મોકલવું)

**સાદી ભાષામાં:** Batch ને **બજારમાં મોકલવાનો છેલ્લો, સૌથી મોટો નિર્ણય**. જેમ કોઈ નવી ઇમારત રહેવા
માટે ખોલતા પહેલાં સરકારી અધિકારી છેલ્લે આવીને "આ ઇમારત રહેવા માટે સલામત છે" કહે, બસ એવું જ.

**શા માટે જરૂરી:** આ પહેલાંના બધા modules (QA Review, QC, Material, પર્યાવરણ, equipment, Yield
વગેરે) ના signal **ફરીથી, તાજેતરમાં (તરત પહેલાં)** ચકાસાય છે — કોઈ જૂનો, stale "બધું સારું" signal
વિશ્વાસમાં નથી લેવાતો.

**ઉદાહરણ:** Release કરતા પહેલા સિસ્ટમ ચકાસે: "Batch પૂરું થયું છે?", "QA Review પૂરું થયું છે?",
"Batch પર કોઈ ખુલ્લો hold છે?", "કોઈ ખુલ્લું deviation/CAPA છે?", "QC test પૂરા થયા?", "Yield/
reconciliation ગણતરી સરખી છે?" — આમાંથી કોઈ પણ "ના" હોય તો release **block** થાય. ફક્ત authorized
વ્યક્તિ (QA Releaser) જ, પોતાનું કારણ (reason) લખીને, સહી સાથે final decision લઈ શકે — અને આ વ્યક્તિ
QA Review કરનાર વ્યક્તિ કરતાં **અલગ જ** હોવી જોઈએ.

**જો આ ના હોય તો:** કોઈ પણ batch, કોઈ પણ ખુલ્લા issue સાથે, સીધું બજારમાં જઈ શકે.

---

## ૧.૯ Yield & Reconciliation (ગણતરીનું સરવૈયું)

**સાદી ભાષામાં:** "કેટલું material વાપર્યું, કેટલું દવા બની" — ની ગણતરી. જેમ ઘરનું budget — કેટલા
પૈસા ખર્ચ્યા, કેટલો સામાન આવ્યો, હિસાબ મળવો જોઈએ.

**શા માટે જરૂરી:** જો material નો હિસાબ ના મળે (દા.ત. ૧૦૦૦ kg વાપર્યું, પણ ફક્ત ૭૦૦ kg દવા/waste/
sample તરીકે account થયું, બાકીના ૩૦૦ kg નો કોઈ હિસાબ જ નથી), તો એ "ખોવાયેલ" material ક્યાં ગયું એ
મોટી ચિંતાનો વિષય છે — ચોરી, ભૂલ, કે બીજી કોઈ ગંભીર સમસ્યા હોઈ શકે.

**ઉદાહરણ:** ૧૦૦૦ kg material issue થયું → ૯૯૫ kg વપરાયું → ૩ kg sample લેવાયા → ૨ kg "process
loss" તરીકે નોંધાયું (કારણ સાથે — દા.ત. "મિક્સરમાં થોડું રહી ગયું"). ૯૯૫+૩+૨ = ૧૦૦૦ — બરાબર મળ્યું,
એટલે "Acceptable". જો આ ગણતરી ના મળે, તો investigation જરૂરી.

**જો આ ના હોય તો:** Material ક્યાંક ખોવાઈ ગયું હોય તો કોઈને ખબર જ ના પડે.

---

## ૧.૧૦ Genealogy (ઇતિહાસ/પગેરું શોધવું)

**સાદી ભાષામાં:** "આ ચોક્કસ material/batch ક્યાંથી આવ્યું, અને ક્યાં-ક્યાં ગયું" — ની સંપૂર્ણ
history/map. જેમ કોઈ parcel ના tracking number થી ખબર પડે કે parcel ક્યાંથી નીકળ્યું, ક્યાં-ક્યાંથી
પસાર થયું, ક્યાં પહોંચ્યું.

**શા માટે જરૂરી:** જો કોઈ એક material lot માં પછીથી ખબર પડે કે ખામી હતી (દા.ત. supplier એ ખોટો
માલ મોકલ્યો), તો તરત ખબર પડવી જોઈએ કે **આ lot કયા-કયા batch માં વપરાયું** — જેથી recall (પાછું
બોલાવવું) બરાબર, ચોક્કસ scope સાથે થઈ શકે, આખું બજાર નહીં.

**ઉદાહરણ:** Material lot "LOT-API-2603" → batch "MJ-PFS-B-2601" માં consumed (વપરાયું) → batch
પેકેજ થયું → ચોક્કસ package/carton માં ગયું. આ આખી ચેઈન (chain) એક ક્લિકમાં જોઈ શકાય છે — **ફક્ત
જોવા માટે**, આ module માં કંઈ પણ નવું ઉમેરવાનું UI નથી, બીજા modules (material/batch/packaging)
પોતે જ આ history આપોઆપ બનાવે છે.

**જો આ ના હોય તો:** ખરાબ material ક્યાં-ક્યાં ગયું એ શોધવા manually, કલાકો સુધી, old paper records
ફેંદવા પડે.

---

## ૧.૧૧ Equipment / Devices (સાધનો)

**સાદી ભાષામાં:** દરેક machine/સાધન "વાપરવા માટે ખરેખર લાયક છે કે નહીં" — એક જ જગ્યાએ રેકોર્ડ. જેમ
કોઈ ગાડી ચલાવવા પહેલાં check કરીએ — "PUC (pollution certificate) valid છે?", "service સમયસર થઈ
છે?", "insurance છે?" — equipment માટે પણ આવું જ.

**શા માટે જરૂરી:** Cleaning, Line Clearance, EM, Aseptic Operation — આ બધા modules **આ જ એક ચેક**
(Equipment ready છે કે નહીં) ને reuse કરે છે, જેથી દરેક જગ્યાએ અલગ-અલગ ના ચકાસવું પડે.

**ઉદાહરણ:** એક equipment "લાયક" ગણાય તો જ જ્યારે: (૧) qualified (પ્રમાણિત) છે, (૨) calibration
(માપ-ચકાસણી) ની તારીખ પસાર નથી થઈ, (૩) maintenance બાકી નથી, (૪) હાલમાં hold પર નથી. આમાંથી કોઈ પણ
એક "ના" હોય, તો એ equipment કોઈ પણ batch માટે વાપરી જ ના શકાય.

**જો આ ના હોય તો:** Expired calibration વાળું, કે maintenance બાકી હોય એવું equipment પણ વપરાય જઈ
શકે, કોઈને ખબર ના પડે.

# ભાગ ૨ — Quality System Modules (ગુણવત્તા સંચાલન)

આ modules ત્યારે વપરાય છે જ્યારે **કંઈક ખોટું થયું હોય, અથવા થવાની શક્યતા હોય** — "શોધવું, તપાસવું,
સુધારવું, ફરી ના થાય એની ખાતરી કરવી" ના ૪ પગલાં દરેક module માં અલગ-અલગ રીતે repeat થાય છે.

---

## ૨.૧ Deviation (આયોજન પ્રમાણે ના થયું)

**સાદી ભાષામાં:** જ્યારે **જે પ્રમાણે planned/approved હતું, એ પ્રમાણે ના થયું** — દા.ત. temperature
નક્કી કરેલ range ની બહાર ગયું, કોઈ step ચૂકી ગયું, machine અચાનક બગડ્યું. જેમ રસોઈ કરતી વખતે ભૂલથી
મીઠું વધારે પડી જાય — "જે થવું જોઈતું હતું, એ ના થયું" ની નોંધ.

**શા માટે જરૂરી:** દરેક "આયોજન પ્રમાણે ના થયું" ઘટનાને **documented, investigated**, અને final
નિર્ણય (decision) સાથે બંધ કરવી જોઈએ — "આ ભૂલ છતાં batch વાપરવા લાયક છે" કે "આ batch reject કરવું
પડશે".

**ઉદાહરણ:** Filling વખતે temperature sensor એ નિયત range ની બહારનું reading આપ્યું → સિસ્ટમ
**આપોઆપ** એક deviation ખોલે (manual યાદ રાખવાની જરૂર નથી) → owner assign થાય → containment
(તાત્કાલિક પગલાં, દા.ત. "batch ને hold પર રાખ્યું") → investigation (મૂળ કારણ શોધવું) → impact
assessment (છ અલગ-અલગ પાસાં — quality, દર્દીની સલામતી, પહેલેથી મોકલાયેલ દવા, validation, data,
regulatory — બધા પર અસર ચકાસવી) → disposition (final નિર્ણય — continue/hold/reject/rework) → બંધ.

**જો આ ના હોય તો:** કોઈ પણ અસામાન્ય ઘટના ભૂલાઈ જાય, ક્યારેય investigate જ ના થાય.

---

## ૨.૨ CAPA — Corrective & Preventive Action (મૂળ કારણ સુધારવું)

**સાદી ભાષામાં:** Deviation/complaint/audit — કોઈ પણ સમસ્યામાંથી જો ખબર પડે કે આ **એક-વખતની ભૂલ
નથી, પણ system ની ખામી છે**, તો એને કાયમ માટે સુધારવા માટેની formal પ્રક્રિયા. જેમ ઘરમાં નળ વારંવાર
leak થતો હોય તો ફક્ત ટુવાલ મૂકવાથી કામ ના ચાલે — plumber ને બોલાવીને મૂળ કારણ (જૂની pipe) બદલવી
પડે.

**શા માટે જરૂરી:** Deviation એ "આ એક ઘટના" નું record છે; CAPA એ "આ ફરી ના થાય" માટેનું action
plan છે — બંને અલગ-અલગ હેતુ માટે જરૂરી છે.

**ઉદાહરણ:** એક Deviation માંથી ખબર પડે કે "Filler-01 નું temperature sensor વારંવાર drift
(ખસી) જાય છે" → CAPA ખોલાય → root cause (મૂળ કારણ) શોધાય → corrective action (હાલની સમસ્યા
સુધારવી — sensor બદલવું) + preventive action (ભવિષ્યમાં ના થાય એ માટે — દા.ત. નિયમિત calibration
schedule બનાવવી) → implement → **effectiveness check** (ખરેખર કામ કર્યું કે નહીં, થોડા મહિના પછી
ફરી ચકાસવું) → બંધ.

**જો આ ના હોય તો:** એ જ સમસ્યા વારંવાર, દર વખતે નવેસરથી, repeat થતી રહે.

## ૨.૩ Nonconformance — NCR (ધારાધોરણ પ્રમાણે નથી)

**સાદી ભાષામાં:** કોઈ material/product ધારાધોરણ (specification) પ્રમાણે નથી — દા.ત. QC test fail
થયું, inspection માં ખામી મળી. જેમ દુકાનમાંથી ખરીદેલ ફળ ઘરે આવીને ખોલતા ખબર પડે કે અંદરથી ખરાબ છે —
"આ વસ્તુ જે quality જોઈતી હતી એ નથી".

**શા માટે જરૂરી:** આવી વસ્તુને તરત **segregate (અલગ રાખવી)** જોઈએ જેથી ભૂલથી વપરાય ના જાય, અને
પછી નિર્ણય લેવાય કે એનું શું કરવું.

**ઉદાહરણ:** QC test માં ખબર પડે કે કોઈ material lot spec ની બહાર છે → NCR ખોલાય → એ lot ને
segregate (અલગ રાખવું, hold) → evaluation (કેટલું ગંભીર છે, ઉપયોગ કરવા લાયક છે કે નહીં) →
disposition — ૫ વિકલ્પ: Rework (ફરી પ્રોસેસ કરવું), Repair (સુધારવું), Return (પાછું મોકલવું),
Scrap (નાશ કરવું), અથવા Use-as-is (concession — ખાસ મંજૂરી સાથે વાપરવું) → verification → બંધ.

**જો આ ના હોય તો:** Spec-બહારની વસ્તુ પણ કોઈ ચેક વગર આગળ વપરાય જઈ શકે.

## ૨.૪ Change Control (ફેરફાર વ્યવસ્થાપન)

**સાદી ભાષામાં:** Product/process/equipment/document — કંઈ પણ **ફેરફાર કરતા પહેલાં**, એ ફેરફારની
અસર (impact) ચકાસવી અને મંજૂરી લેવી ફરજિયાત. જેમ ઘરનું નવીનીકરણ (renovation) કરતા પહેલાં architect
પાસે નકશો ચકાસાવવો પડે — અચાનક દિવાલ તોડી નાખવાથી આખું ઘર પડી શકે.

**શા માટે જરૂરી:** Manufacturing માં અચાનક, બિનયોજિત ફેરફાર ખૂબ મોટું risk છે — નાનો ફેરફાર પણ
આખી દવાની ગુણવત્તાને અસર કરી શકે.

**ઉદાહરણ:** Recipe માં "કેટલું ભરવું" (fill volume) બદલવું હોય → draft (ફેરફારની વિગત લખવી) →
impact assessment (regulatory, validation, training — બધા પાસાં પર અસર ચકાસવી) → approve (સહી
સાથે મંજૂરી) → implement (ખરેખર ફેરફાર કરવો) → verify (ફેરફાર ખરેખર કામ કરે છે એ ચકાસવું, સહી સાથે)
→ close (સહી સાથે બંધ). જો ફેરફાર પછી ખબર પડે કે કામ ના કર્યું, તો **Rollback** (પાછું જૂની
સ્થિતિમાં લઈ જવું) પણ કરી શકાય.

**જો આ ના હોય તો:** કોઈ પણ વ્યક્તિ, ગમે ત્યારે, કોઈ ચકાસણી વગર recipe/process બદલી શકે.

---

## ૨.૫ Complaints (ગ્રાહક ફરિયાદ)

**સાદી ભાષામાં:** બજારમાંથી (દર્દી/doctor/distributor પાસેથી) આવતી ફરિયાદ — intake, investigation,
અને **સરકારને જણાવવું પડે કે નહીં** એનો નિર્ણય. જેમ કોઈ product ની ઓનલાઇન ફરિયાદ આવે ત્યારે કંપની
પહેલા સાંભળે, પછી તપાસે, પછી જરૂર પડે તો replace/refund કરે.

**શા માટે જરૂરી:** દર્દી પાસેથી આવતી ફરિયાદ એ "field માં ખરેખર શું થયું" ની સૌથી સીધી માહિતી છે —
અને ઘણી વાર regulatory authority (દા.ત. US માં FDA) ને જાણ કરવી કાયદેસર ફરજિયાત હોય છે.

**ઉદાહરણ:** Doctor ફરિયાદ કરે કે "સિરીંજનું plunger અટકી જાય છે, દવા પૂરી નથી જતી" → ફરિયાદ નોંધાય →
triage (કેટલું ગંભીર છે નક્કી કરવું) → investigation → **reportability assessment** (શું FDA ને
જણાવવું પડે? — સહી સાથે નિર્ણય) → response (ગ્રાહકને જવાબ) → close.

**જો આ ના હોય તો:** ગંભીર ફરિયાદ પણ ધ્યાન બહાર રહી જાય, regulatory જવાબદારી ચૂકી જાય.

---

## ૨.૬ Field Actions (રિકોલ/પાછું બોલાવવું)

**સાદી ભાષામાં:** જ્યારે કોઈ ખામી confirmed થાય (ફરિયાદ/deviation/CAPA માંથી), ત્યારે બજારમાંથી
affected (અસર પામેલ) product **પાછું બોલાવવું (recall)** અથવા સુધારવું (correction). જેમ car
company ને ખબર પડે કે કોઈ મોડેલમાં brake ની ખામી છે, તો એ specific મોડેલ પાછા બોલાવે છે.

**શા માટે જરૂરી:** ખામીવાળી દવા બજારમાં રહેવા દેવી ખૂબ risky છે — પણ આખું બજાર ખાલી કરવું (બિનજરૂરી
રીતે) પણ નુકસાનકારક છે, એટલે **ચોક્કસ scope (કયા lot, કયા customer)** નક્કી કરવું જરૂરી.

**ઉદાહરણ:** Complaint માંથી ખબર પડે કે ચોક્કસ lot માં plunger ની ખામી confirmed છે → field action
ખોલાય → scope define (કયા lot affected છે — manually લખવું પડે) → regulatory decision (સહી સાથે) →
approve (સહી સાથે) → notify (distributor/customer ને જણાવવું) → reconciliation (કેટલા પાછા
આવ્યા, કેટલા બાકી — બધા પાછા ના આવે ત્યાં સુધી બંધ ના થાય) → effectiveness check → close (સહી
સાથે).

**જો આ ના હોય તો:** ખામીવાળી દવા બજારમાં ફરતી રહે, કોઈ વ્યવસ્થિત પાછી ના બોલાવાય.

## ૨.૭ Internal Audits (આંતરિક તપાસ)

**સાદી ભાષામાં:** કંપની **પોતે જ પોતાની ભૂલ શોધે** — બહારથી કોઈ inspector આવે એ પહેલાં. જેમ પરીક્ષા
પહેલાં જાતે mock-test આપીને પોતાની ભૂલો શોધી લેવી, જેથી real પરીક્ષામાં ઓછી ભૂલ થાય.

**શા માટે જરૂરી:** External inspector (સરકારી અધિકારી) ને ભૂલ મળે એ પહેલાં, કંપની પોતે ભૂલ શોધીને
સુધારી લે તો ઘણું સારું — અને કાયદેસર રીતે પણ નિયમિત internal audit ફરજિયાત છે.

**ઉદાહરણ:** Sterile manufacturing area નો audit → lead auditor + team નક્કી થાય (**ખાસ ચેક:**
auditor પોતે એ જ area/team નો ભાગ ના હોવો જોઈએ — "પોતાનું કામ પોતે ચકાસી ના શકાય") → audit શરૂ
(સહી સાથે) → finding નોંધાય (દા.ત. "cleaning log માં ૩ shift ની ખોટ") → response (સુધારો શું
કરાશે) → verify (સહી સાથે, independent વ્યક્તિ દ્વારા) → close (સહી સાથે).

**જો આ ના હોય તો:** કંપનીની પોતાની ભૂલો ક્યારેય જાતે ખબર જ ના પડે, સીધી બહારના inspector પાસેથી જ
ખબર પડે — જે ઘણું મોડું અને નુકસાનકારક હોય શકે.

## ૨.૮ Risk Register (જોખમ આકારણી)

**સાદી ભાષામાં:** કોઈ પણ process/equipment/supplier સાથે જોડાયેલ **જોખમ (risk) નું formal
મૂલ્યાંકન** — કેટલું ગંભીર, કેટલી વાર થવાની શક્યતા, કેટલું સરળતાથી ખબર પડે. જેમ ઘર ખરીદતા પહેલાં
"આ વિસ્તારમાં પૂર આવવાનું જોખમ કેટલું છે" ચકાસવું.

**શા માટે જરૂરી:** દરેક નિર્ણય પાછળ **કેમ** એ નિર્ણય લેવાયો એનું સ્પષ્ટ, ફરીથી-ચકાસી-શકાય એવું
(reproducible) કારણ હોવું જોઈએ — "આ risk સ્વીકારી" કહેવું પૂરતું નથી, "કેમ સ્વીકારી" પણ લખાયેલું
હોવું જોઈએ.

**ઉદાહરણ:** "Aseptic filling દરમિયાન contamination નું જોખમ" → initial assessment (severity ×
occurrence × detectability = score) → controls ઉમેરાય (દા.ત. "redundant pressure interlock
લગાવ્યું") → residual assessment (controls પછી score ફરી ગણાય, ઓછો થવો જોઈએ) → accept (role +
કારણ સાથે — ખાસ વાત: આ **સહી વગર** થાય છે, ફક્ત કારણ લખવું પડે) → periodic review (સમય જતાં ફરી
ચકાસવું, **સહી સાથે**, risk ના owner કરતાં અલગ વ્યક્તિ દ્વારા).

**જો આ ના હોય તો:** જોખમ વિશે નિર્ણયો મૌખિક/unwritten રહી જાય, સમય જતાં "કેમ આ નિર્ણય લીધો હતો" કોઈને
યાદ ના રહે.

---

## ૨.૯ Supplier Cases — SCAR (સપ્લાયર ફરિયાદ)

**સાદી ભાષામાં:** જ્યારે કોઈ supplier (material આપનાર) નો material ખામીવાળું આવે, ત્યારે supplier
ને formal રીતે જવાબદાર ઠેરવવાની પ્રક્રિયા. જેમ કોઈ દુકાનદાર પાસેથી ખરાબ માલ આવે તો દુકાનદારને
ફરિયાદ કરીએ, જવાબ માંગીએ, અને જો વારંવાર થાય તો એ દુકાનદાર પાસેથી ખરીદવાનું બંધ કરી દઈએ.

**શા માટે જરૂરી:** Supplier નો material કંપનીની પોતાની ગુણવત્તાનો જ ભાગ છે — ખરાબ supplier ને
ઓળખીને **રોકવો** (suspend) જરૂરી છે, નહીં તો એ જ ખામી repeat થતી રહે.

**ઉદાહરણ:** NaOCl (એક chemical) ના lot નો assay test fail થયો → case ખોલાય → SCAR (formal ફરિયાદ
patter) supplier ને મોકલાય → supplier નો જવાબ (root cause + corrective action) → review → close —
**ખાસ મહત્વનું:** close કરતી વખતે નિર્ણય લેવાય કે supplier ને "સસ્પેન્ડ" કરવો કે નહીં. જો સસ્પેન્ડ
થાય, તો **એ જ ક્ષણથી**, એ supplier પાસેથી આવતો કોઈ પણ નવો material receipt આપોઆપ "hold" પર જાય —
મેન્યુઅલી યાદ રાખવાની જરૂર નથી, સિસ્ટમ પોતે જ રોકે છે.

**જો આ ના હોય તો:** ખરાબ supplier પાસેથી material આવવાનું ચાલુ જ રહે, કોઈ રોકતું નથી.

---

## ૨.૧૦ Documents (નિયંત્રિત દસ્તાવેજો)

**સાદી ભાષામાં:** કંપનીના બધા SOP (Standard Operating Procedure — "કેવી રીતે કરવું" ની સૂચના),
policy, specification — આનું "કોણે ક્યારે approve કર્યું, ક્યારે effective થયું, ક્યારે જૂનું
(obsolete) થયું" નું સંચાલન. જેમ કોઈ કોલેજની syllabus "version 1", "version 2" — દરેક version
ની પોતાની તારીખ અને approval હોય.

**શા માટે જરૂરી:** જો જૂની, ખોટી SOP વાપરીને કોઈ કામ કરે, તો આખું batch ખોટી રીતે બની શકે — "આ
દસ્તાવેજ ખરેખર હાલમાં અસરકારક (effective) છે" એ ખાતરી કરવી ખૂબ જરૂરી છે.

**ઉદાહરણ:** "Aseptic Gowning SOP" ની નવી version → draft → review → release (સહી સાથે, જે વ્યક્તિએ
લખ્યું એ પોતે release ના કરી શકે) → effective → જરૂર પડે તો obsolete. દરેક version નો પોતાનો
"ફિંગરપ્રિન્ટ" (hash — ફાઈલનો ડિજિટલ ઓળખ-કોડ) સચવાય છે, જેથી પાછળથી કોઈ ફાઈલ સાથે ચેડાં થયા છે કે
નહીં ખબર પડે.

**જો આ ના હોય તો:** કોઈ પણ વ્યક્તિ, ગમે ત્યારે, SOP માં ફેરફાર કરી શકે, કોઈ track જ ના રહે કે કયું
version હાલમાં ઉપયોગમાં છે.

---

## ૨.૧૧ Training (તાલીમ અને યોગ્યતા)

**સાદી ભાષામાં:** કોઈ પણ વ્યક્તિ કોઈ ચોક્કસ કામ કરે એ પહેલાં, એ **ખરેખર એ કામ માટે તાલીમ પામેલ/
યોગ્ય છે** એની ખાતરી. જેમ ડ્રાઇવિંગ લાયસન્સ વગર ગાડી ના ચલાવી શકાય, બસ એવું જ — "Aseptic gowning"
જેવું સંવેદનશીલ કામ કરવા માટે ચોક્કસ તાલીમ + certificate જોઈએ.

**શા માટે જરૂરી:** Untrained (તાલીમ વગરની) વ્યક્તિ regulated કામ કરે તો ભૂલ થવાની શક્યતા ખૂબ વધી
જાય છે.

**ઉદાહરણ:** "Aseptic Gowning SOP" release થયા પછી → training requirement બને (આ document સાથે
જોડાયેલ) → ચોક્કસ વ્યક્તિને assignment અપાય (સહી સાથે — ખાસ કારણ: record હજુ બન્યો જ નથી ત્યારે
પણ સહી લેવી પડે, એક ખાસ વ્યવસ્થા) → વ્યક્તિ training પૂરી કરે → **અલગ** વ્યક્તિ assessment કરે (પાસ/
ફેલ, score સાથે) → પાસ થાય તો "Qualification" (યોગ્યતા પ્રમાણપત્ર) અપાય. આ qualification વગર, એ
વ્યક્તિ ખરેખર batch ના ચોક્કસ step શરૂ જ નહીં કરી શકે — સિસ્ટમ પોતે રોકે છે. ખાસ કિસ્સામાં (દા.ત.
બીજી કંપનીમાં પહેલેથી equivalent તાલીમ લીધેલ હોય), "Waiver" (મુક્તિ) પણ આપી શકાય — પણ એ કોઈ ઈ-સહી
વગર, ફક્ત લેખિત કારણ સાથે.

**જો આ ના હોય તો:** તાલીમ વગરની વ્યક્તિ પણ સંવેદનશીલ કામ કરી શકે, કોઈ રોકતું નથી.

---

## ૨.૧૨ Quality Metrics (ગુણવત્તાના આંકડા)

**સાદી ભાષામાં:** "આપણે લીધેલા સુધારાના પગલાં (CAPA/SCAR/Field Action) ખરેખર કામ કરી રહ્યા છે કે
નહીં" — એનું numbers (આંકડા) દ્વારા સાબિતી. જેમ કોઈ diet plan શરૂ કર્યા પછી, "ખરેખર વજન ઘટ્યું કે
નહીં" જોવા માટે નિયમિત weight માપવું.

**શા માટે જરૂરી:** "અમે સુધારો કર્યો" કહેવું પૂરતું નથી — numbers થી સાબિત કરવું જોઈએ કે ખરેખર
સુધારો થયો (દા.ત. deviation ની સંખ્યા ઘટી કે નહીં).

**ઉદાહરણ:** "Deviation rate" નામનું એક metric (માપદંડ) વ્યાખ્યાયિત થાય → release (સહી સાથે) →
દર ૩ મહિને snapshot (ફોટો જેવું — એ સમયની real ગણતરી) લેવાય → management review માં ફ્રીઝ (સહી
સાથે, બદલી ના શકાય) → અલગથી, કોઈ ચોક્કસ CAPA ની "effectiveness check" (એ CAPA ખરેખર કામ કરી રહ્યું
છે કે નહીં) manually ખોલીને ચકાસાય.

**જો આ ના હોય તો:** કોઈ પણ સુધારાનું પગલું "કામ કરે છે" એવું ધારી લેવાય, ખરેખર ચકાસાય જ નહીં.

# સારાંશ — એક-લીટીમાં બધા Modules

| Module | એક લીટીમાં |
|---|---|
| Cleaning | Equipment ફરી વાપરતા પહેલાં ચોખ્ખું છે એની ખાતરી |
| Line Clearance | નવું batch શરૂ કરતા પહેલાં જગ્યા ખાલી/ચોખ્ખી છે એની ખાતરી |
| Sterilization | Equipment/ફિલ્ટર જીવાણુ-મુક્ત છે એની ખાતરી |
| Environmental Monitoring | રૂમની હવા/સપાટી ચોખ્ખી છે એની સતત ખાતરી |
| Aseptic Operation | ખરેખર દવા ભરવી — બધું તૈયાર હોય તો જ |
| Packaging | Label/પેકિંગ ની ગણતરી સરખી રાખવી |
| QA Review | Release પહેલાં batch નું આખું ચિત્ર ફરી જોવું |
| Release | બજારમાં મોકલવાનો છેલ્લો, સંપૂર્ણ-ચકાસાયેલ નિર્ણય |
| Yield & Reconciliation | Material ની ગણતરીનું સરવૈયું મળવું જોઈએ |
| Genealogy | કોઈ પણ વસ્તુનું ઇતિહાસ/પગેરું શોધવું |
| Equipment/Devices | દરેક સાધન વાપરવા લાયક છે કે નહીં — એક જ જગ્યાએ રેકોર્ડ |
| Deviation | આયોજન પ્રમાણે ના થયું — નોંધવું, તપાસવું, નિર્ણય લેવો |
| CAPA | મૂળ કારણ શોધીને કાયમ માટે સુધારવું |
| Nonconformance (NCR) | Spec-બહારની વસ્તુનું શું કરવું — નિર્ણય |
| Change Control | કોઈ પણ ફેરફાર પહેલાં અસર ચકાસવી, મંજૂરી લેવી |
| Complaints | ગ્રાહક ફરિયાદ — તપાસ + regulatory જણાવવું કે નહીં |
| Field Actions | ખામીવાળી દવા બજારમાંથી પાછી બોલાવવી |
| Internal Audits | કંપની પોતે પોતાની ભૂલ શોધે |
| Risk Register | જોખમનું formal, લેખિત મૂલ્યાંકન |
| Supplier Cases (SCAR) | ખરાબ supplier ને જવાબદાર ઠેરવવો, જરૂર પડે તો રોકવો |
| Documents | SOP/policy ના version/approval નું સંચાલન |
| Training | કામ કરનાર વ્યક્તિ ખરેખર યોગ્ય/તાલીમ પામેલ છે એની ખાતરી |
| Quality Metrics | સુધારાના પગલાં ખરેખર કામ કરે છે એની numbers થી સાબિતી |

**સૌથી મહત્વની વાત, બધા modules માટે સરખી:** દરેક જગ્યાએ "જે વ્યક્તિએ કામ કર્યું" અને "જે વ્યક્તિએ
ચકાસ્યું/મંજૂર કર્યું" — એ **બે અલગ-અલગ વ્યક્તિ** હોવી જોઈએ (independence). આ એક જ principle આખા
system માં ફરી-ફરી દેખાય છે, કારણ કે "પોતાનું કામ પોતે ચકાસવું" ભરોસાપાત્ર નથી ગણાતું.
